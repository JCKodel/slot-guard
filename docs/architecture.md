# Architecture

`hooks/register.js` keeps one state machine per agent turn, keyed by agent ID (a `/clear` changes the session ID mid-flight, never the agent). The first `turn.step` acquires one ticket in the global `agent` pool. Only `turn.step` waits for a grant: tools run on the ticket whether granted or queued. Rotation (cooperative multitasking): a step's acquire carries `rotate` when the agent has no step or tool in flight, a tool's start sends `op: rotate` under the same condition, and the heartbeat sends it for agents in a long tool with no step in flight. The coordinator rotates a ticket granted for at least `quantum` seconds (config, default 60) only if another ticket is queued: in one transaction it becomes queued with rank 1 and a position after every ticket (`pos`), and `_promote` grants the next. Grants record `since`; queue order is rank, then `coalesce(pos, seq)`. A subagent claiming its parent's parked ticket sends `fresh`, restarting `since`. Every rotation decision runs under the agent's lock, the same lock a step's admission takes, so no step can start between the check and the rotation; rotation therefore never puts more agents in a model call than the limit (forced subagent admissions are the documented overdraft). A queued ticket of rank 1 waiting 300 s (`coalesce(waited, created)`) is raised to rank 0, so new subagents cannot starve prompts or rotated agents. `turn.complete` closes the state; release waits until outstanding ordinary work has unwound.

Each agent tracks busy operations (model streams and ordinary tools) and wait operations. `Agent`, legacy `Task`, blocking `TaskOutput`, `AskUserQuestion`, `ExitPlanMode`, and `Bash` commands that run `claude` are waits. A `tool.check` verdict of `ask` still unanswered after 15 s turns the admitted call into a wait, so a permission prompt does not hold a slot while the person is away. The delay matters in auto mode, where most calls are an `ask` answered by the classifier within seconds: yielding at once sent every agent to the back of FIFO on each tool call. In rare parallel timing (another tool of the same agent requeued ahead of it) the `tool.check` hook can exceed its budget waiting for the agent's lock; the engine's verdict stands and the state stays consistent. An agent with child waits and no busy operations releases its ticket. It obtains a new generation ticket before resuming inference or ordinary tool work, entering at the back of FIFO. If an ordinary tool is running alongside a child wait, the agent remains counted. State transitions are serialized within the mod; tool execution itself remains concurrent.

Subagents follow exactly the same admission path as main agents and release on their own `turn.complete`. A new turn for an agent whose previous turn never reported completion closes that turn instead of failing. No two-pool admission or parent-only reservation remains. A tool outside an admitted agent turn is denied, rather than silently bypassing admission. Both inference and tool hook error fallbacks refuse to call their next handler.

Each coordinator call runs the fixed argv `python3 guard.py client` with `cwd` set to the installed plugin root. JSON stdin carries only coordination identifiers. Python identifies the native Claude ancestor and uses SQLite WAL plus `flock` to serialize FIFO admission across processes. Owner birth identity protects against PID reuse. Unknown liveness retains reservations; confirmed dead owners are reaped on a subsequent call.

A released generation stays as a tombstone until its process dies or for one hour, preventing delayed acquires from reviving canceled work.

## Liveness inside a living process

Owner death alone cannot free a ticket the owner forgot, because the owner is the long-lived Claude process. Four mechanisms bound that:

1. **Retried release.** Release never throws; a failed release (an interrupted dispatch aborts its own calls, a lock timeout) is retried at the agent's next step, at `turn.complete`, and by the heartbeat.
2. **Lease.** `session.start` starts a 30 s `$.clock.every` heartbeat that renews (`touch`) every ticket the mod is using. The coordinator releases a ticket of a heartbeating client not renewed for 300 s. Rows written by older clients (no load ID) never expire, so mixed versions stay safe.
3. **Idle release.** A ticket with no busy work, no wait and no acquisition in progress for 120 s is released by the heartbeat: a turn whose end was never heard cannot keep its slot.
4. **Adoption.** Each module load has its own ID. On `session.start` it releases every ticket of the same owner held by another load (a hot reload or plugin update discards the previous load's state and timers).

## Subagents and the stall limit

Claude Code fails a subagent whose model step shows no progress for 600 s, and waiting in a `turn.step` hook is no progress. Three mechanisms keep subagents under that bound. `agent.spawn` records each subagent's parent. A parent yielding for `Agent`/`Task` parks its granted ticket instead of releasing it; the first `enter` of one of its subagents (or of the parent itself) claims it, and the heartbeat releases an unclaimed one after 60 s. Tickets carry a rank: 0 for subagents and later generations of a turn, 1 for a turn's first; `_promote` grants by rank, then sequence. A subagent's step still queued after 420 s (the stall clock runs from the step's start, so the model keeps 180 s for its first chunk) sends `force`, which grants it regardless of the limit unless the limit is 0; the pool stays over the limit until it drains, and `auto.log` records the overdraft.

A sprint (`/slots sprint [all] [M]`, op `sprint`) is the other overdraft, for urgent work. The `sprints` table holds a session ID (`*` for every session) and an end time, at most 60 minutes ahead; `minutes: 0` ends every sprint, and `reap` drops expired rows. While a session sprints, `_promote` grants its queued tickets regardless of the limit, unless the limit is 0 (a pause stops a sprint too), and `_rotate` leaves its granted tickets alone. Sprint tickets count as granted, so other sessions start nothing new until the pool drains under the limit; once the sprint ends its tickets rotate like any other.

## Automatic limit

The mod reports Claude Code's usage windows (`five_hour`, `seven_day`: percentage used, reset time) from `session.measure` and its heartbeat via `$.session.usage()`, only when they change. The coordinator keeps one row per window, the highest percentage for the same reset time (sessions read it from different responses), and drops readings of a window that already ended. A reading more than 5 points under the stored one for the same reset time is a restart of the account's window (a plan change): it replaces the row, clears that window's rate log, and the limit starts again from the normal limit. `reset` (from `/slots reset` or `guard.py reset`) clears the control table and, with `usage`, every reading; `configure` (`/slots agents|max|auto|quantum`, `guard.py configure`) rewrites the configuration and then resets the control table, so a change applies at once rather than one step per 600 s.

On every operation the coordinator computes the effective limit. A window's pace is the budget left (to 95%) over what the recent burn rate would spend in the time left; 1 is on pace. The rate comes from a log of readings (percent changes with their time): over the last hour for the five-hour window (at least 10 minutes apart). The weekly window counts working time instead of clock time: `activity` holds the start of every 5-minute bucket in which the coordinator saw a granted ticket (every call, heartbeats included, recomputes the limit), kept 8 days and through resets. Its rate is percent per working second over the last 4 working hours of readings (spanning at least 2), and the time left is multiplied by the working share: working time over the last 7 days (since the first bucket, if later) plus 8 hours, over that span plus 24 hours, at least 1/24. Without enough readings, pace is the share of budget left over the share of time left. The five-hour window votes a slot down below 0.9 (floor 1) and lets it rise above 1.1; the weekly window votes down below 0.75 and up above 1.1, floor 1. The weekly window is also held to a linear quota (used percent never above elapsed share × 100), as a separate `line` vote (down below 1.0, up above 1.1, floor 1): (margin to the line + the line's rise over 4 hours) ÷ (recent rate per working second × 4 hours), with no working-share discount, so nonstop work counts as such; none without a rate. A reading over the line sets the effective limit to 0 until the line reaches it (start + percent × length ÷ 100), demoting granted tickets as at 95%; the stepped limit is stored apart and keeps stepping, so work resumes from it, and `control.line` marks the reason for the statusline. Any down vote lowers the limit by one, to the smallest floor among the voters; it rises to the normal limit only when every window allows it. With a configured `max`, it rises above normal only while every window's pace exceeds 1.25 and steps back toward normal once any is under 1.1. One change per 600 s at most, except after a pause: when no ticket has been granted for an hour (the last `activity` bucket, read before the current call marks its own), the limit takes every step the current paces call for at once, up or down, so a morning starts at the limit the readings support instead of climbing one slot per 600 s from where the evening left it. The first 900 s of a window are ignored. A window at or past 95% sets the limit to 0 until its reset time: granted tickets are demoted to queued, keeping their sequence, so agents wait at their next step or tool and resume in FIFO order once the reading expires. Without a valid reading the configured maximum applies; after a pause the limit restarts from the maximum. Acquire responses carry `paused_until` during a pause, which the mod shows in the status line, and waiting coordinators poll every 2 s instead of 0.25 s. A session still running an older version ignores the new tables: its coordinator calls grant up to the maximum, re-granting paused tickets, so a pause only holds once every participating session runs 0.5.0.

An evicted or expired ticket rejoins the back of FIFO once on the agent's next operation; a second refusal stops the turn. Under coordinator lock contention an acquirer keeps waiting rather than aborting the turn; other operations fail and are retried. Configuration initialization is atomic. Legacy configuration migrates only when every recorded legacy owner is confirmed dead, then replaces both limits with their minimum. Restarting participating sessions after an update is still recommended; a hot replacement releases the previous load's tickets.

`statusline.py` reads the one pool without modifying state. The optional wrapper preserves the previous statusline and appends the agent count. Detached tools and uninstrumented model paths remain outside this cooperative limiter; it is not a security boundary or token budget.
